# PI from Scratch

> 从零手撕一个 AI Coding Agent

## 全书结构

### 第一章：五个文件，各管各的

**目标**：读完知道每个模块是干嘛的，脑子里有张地图。

**内容**：
1. 先看全貌：总共 5 个文件，~750 行，对标 pi 上万行
2. 每个模块一段话讲清楚"做什么"和"不做什么"：
   - `llm.ts`：跟 LLM API 说话的翻译官，进去是 Context，出来是 4 种事件流
   - `agent.ts`：整个项目的灵魂，就一个 while 循环
   - `tools.ts`：4 个纯函数，能读能写能改能跑命令
   - `tui.ts`：最糙的终端界面，能打字能看输出能 Ctrl+C
   - `cli.ts`：胶水层，把上面四个粘起来，顺便存个盘
3. 跟 pi 的对应关系，砍了什么、为什么砍
4. 一张架构图（文字版，不依赖 mermaid 渲染）

**篇幅**：~1500 字


### 第二章：从一个 while 循环开始

**目标**：从数据流出发，一步步拼出完整代码。不是"我给你看代码"，是"我们需要什么，就造什么"。

**行文线索**：

1. **起点：agent 到底是什么？**
   - 一句话定义：能调工具的 LLM，自己决定下一步做什么
   - 那核心就是一个循环：问 LLM → LLM 说要调工具 → 调完把结果喂回去 → 再问
   - 先写出最简版伪代码（10 行以内），把骨架亮出来

2. **第一个问题：怎么跟 LLM 说话？**
   - 引出 `llm.ts` 的 `stream()` 函数
   - 先讲 Context 是什么（就是聊天记录，纯 JSON）
   - 再讲 SSE 流式响应怎么解析成 4 种事件
   - 对比 pi 的 pi-ai：我们只做单 provider，把"脏活"砍干净
   - 讲 `contextToOpenAIMessages`：为什么要做格式转换（nanopi 内部格式 vs OpenAI 格式）

3. **第二个问题：LLM 要调工具，工具哪来？**
   - 引出 `tools.ts`
   - 4 个工具的设计：为什么是这四个（读/写/改/跑，最小完备集）
   - `edit` 为什么用字符串匹配而不是行号
   - 输出截取：工具输出可能巨大，得截

4. **把循环补完整：agent loop**
   - 回到第 1 步的伪代码，把真实代码填进去
   - `runAgent()` 逐段讲解：
     - 流式收集 text 和 tool_calls
     - 没有 tool_call？循环结束，模型说完了
     - 有 tool_call？执行，结果塞回 context，继续循环
   - 两个边界情况：
     - `max_tokens` 截断：tool 参数可能是半截 JSON，别执行，告诉模型重发
     - `aborted`：用户按了 Ctrl+C，丢掉 tool_calls，收工

5. **context 会撑爆的：compaction**
   - 聊久了消息越来越多，context 有上限
   - 最简方案：消息超过 50 条，让 LLM 总结旧的，用摘要替换
   - 对比 pi：原版 970 行做精确 token 估算，我们用消息条数近似

6. **得有个界面吧：tui**
   - 引出 `tui.ts`
   - readline 读输入，process.stdout.write 流式输出
   - Ctrl+C 的处理：busy 状态下才拦截，否则交给系统
   - 对比 pi 的 pi-tui：differential renderer 是什么，为什么不碰
   - **关键洞察：UI 只是 AgentEvent 的消费者**
     - `runAgent()` 吐出的是一串结构化事件（assistant_text / tool_call / tool_result / turn_end）
     - tui 只是用 `process.stdout.write` 消费它，但这不是唯一方式
     - 这个结构跟前后端分离一模一样：agent 是后端 API，UI 是前端，中间靠事件协议通信
   - **范例：换个"前端"**
     - 写一个 20 行的 HTTP server，把 AgentEvent 用 SSE 推给浏览器
     - 或者更简单：写个函数把 AgentEvent 攒成纯 JSON 返回，模拟 REST API
     - 重点不是这个 demo 本身，而是让读者看到：agent 核心逻辑一行没动，只是换了个消费端
     - 这也是 pi 的架构哲学：pi-agent-core 完全不知道 pi-tui 的存在

7. **最后把它们粘起来：cli**
   - 引出 `cli.ts` 的 `main()` 函数
   - 事件转发：agent 的 AgentEvent → tui 的 print 方法，一个 switch 搞定
   - session 持久化：每轮结束 append 到 JSONL，下次启动加载回来
   - 整个数据流走一遍：用户输入 → context → LLM → tool → context → LLM → ... → 屏幕

**篇幅**：~5000 字


### 第三章：跑起来看看（可选）

**目标**：实际跑一遍，看数据怎么流的。

**内容**：
1. 环境准备：npm install，设 API key
2. 跑一个简单任务："把 hello.txt 改成大写"
3. 逐步看终端输出，对应到代码里的每个环节
4. 看 session.jsonl 里存了什么

**篇幅**：~1000 字


## 写作约束

- 中文为主，技术术语保留英文（Context、stream、tool_call 等）
- 不用破折号（——），用逗号或句号断句
- 禁止翻案腔："不是A而是B"、"不在于A在于B"、"与其说A不如说B"、"看似A实则B"。判断从正面下，直接说结论
- 避免 AI 味的总结句、过渡句和元叙述（"让我们来看看"、"总结一下"、"接下来"、"用大白话说就是"、"简单来说"、"先把这件事说清楚"之类，直接说事情本身，别加"我要用什么方式跟你说"或"我要把什么搞清楚"这种框）
- 语气像在跟朋友讲，偶尔可以粗一点（"这破玩意儿"、"别管那些花里胡哨的"）
- 代码块只放关键片段，不贴完整文件（完整代码让读者自己去看 src/）
- 每引入一个新概念前，先用一句话说清楚"为什么需要它"
- 不要反复说同一件事。一个信息在最合适的地方讲一次就够了。"600 行"、"砍了什么"这类标签说一次就行，翻来覆去讲读者会烦
- 不要提前透露后面章节才展开的设计细节。第一章只说"是什么"，不展开"怎么做的"
- 段落式写法为主，少用列表。要讲三件事就写三段话，别上来就 1. 2. 3.
- 适当用图辅助理解（架构图、数据流图、时序图等），先用 `[图：xxx]` 占位描述，后续替换为正式图
- 专业术语首次出现时用 `>` 引用块加注释，用一两句大白话解释清楚。比如 SSE、async generator、context window、JSON Schema 这类词，不能假设读者都知道
